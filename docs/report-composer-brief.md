(content-engine, quality-loop, dashboard, product-layer, document-ingestion,

## Framing
This is the **third consumer of the substrate**, after content generation and campaign
proposal. It is what turns the platform from a *production engine* into a *production +
insight engine*. The job: read the org's substrate (metric_points), memory (query_memory
patterns), production lane (artifacts, runs, costs), and campaigns — and produce a coherent
narrative READOUT for a human audience up the chain (board, CEO, sales leadership).

The product position this build creates:
> "We don't just generate marketing content. We tell the story of how marketing is doing."

That second sentence is the differentiator. Hold it as the quality bar — every output must
read as a *story* with insight, not a dashboard with sentences around it.

## THE LOAD-BEARING ARCHITECTURAL PRINCIPLE
**One intelligence engine, three render strategies.** Do not write three independent templates
that produce three slightly-different reports. The engine produces ONE structured intelligence
object; each audience strategy selects and frames a DIFFERENT cut of it. Audiences differ not
only in tone, but in what gets emphasized, what gets omitted, and what the report is trying to
do for the reader.

- **Board update** — *defensive posture*: pipeline contribution, efficiency, trajectory over
  multiple periods. Risks and asks surfaced. NOT tactical detail.
- **CEO weekly digest** — *signal-dense*: what changed since last week, what's notable, what
  needs attention. 2–3 bullets. Memory pattern detection shines here. Almost no tactical
  content.
- **Sales leadership update** — *operationally collaborative*: what marketing produced that
  sales should know about, where pipeline help is coming from, what's about to land. Framed
  *to* sales, not *about* marketing.

If a render strategy ever degenerates into "the same content with different headings," the
build failed. There's a test (see below) that the same intelligence object renders to
materially different narratives across the three audiences.

## The intelligence engine (the shared core, built once)
Create `app/reports/intelligence.py` exposing:

```
build_report_intelligence(org_id, *, product_id=None, scope, lookback_days=30) -> ReportIntelligence
```

`scope` is one of:
- `{"kind": "time_window", "start": date, "end": date}`
- `{"kind": "campaign", "campaign_id": ...}`

The engine reads, ALL via scoped():
- **The substrate** — metric_points within scope, with the baseline-vs-attributed
  distinction preserved (the existing dashboard discipline). Funnel aggregation.
- **Memory** — query_memory(...) for relevant patterns (channel/audience/content_type),
  honoring the watching/insufficient discipline already in place. Thin patterns surface as
  "what we're watching," never as findings.
- **Production lane** — runs + artifacts in scope: count produced, count approved, total
  cost. Same numbers the existing dashboard production lane already exposes.
- **Campaigns** — campaigns within scope (or the named one), with their status, plan, and
  attributed assets.
- **Content** — top-performing pieces (by attributed conversions where data supports it,
  honestly silent where it doesn't).

Returns a structured `ReportIntelligence` object:
```
{
  scope: {...},
  period_summary: {...},        # funnel totals + deltas vs prior period
  notable_changes: [...],       # rule-based: stage-up/stage-flat, channel emerged, campaign
                                # outperformed/underperformed
  memory_highlights: [...],     # high/moderate confidence patterns relevant to the scope
  watching: [...],              # insufficient patterns — honestly named
  production: {...},            # what we made + cost
  campaigns: [...],             # campaigns in scope, status, results where attributed
  top_content: [...],           # attributed top performers, with evidence
  open_questions: [...],        # things the system can't answer from data alone
  honesty_notes: [...],         # data gaps, untagged volume excluded, "no prior period" caveats
}
```

The engine is deterministic at the structural level (aggregation, ranking, pattern selection)
— same discipline as memory. Narrative copy is generated by render strategies (LLM-touching),
but the *intelligence* is computed in Python.

**Empty / thin scope is honest.** If lookback has no data, the engine returns a populated
`honesty_notes` and minimal-but-truthful sections — the report becomes a short "not enough
data to say much yet" rather than confabulated content.

## Render strategies (three implementations of the same interface)
Create `app/reports/renderers/` with one module per audience:
- `board.py` — `render_board(intelligence) -> ReportDraft`
- `ceo_weekly.py` — `render_ceo_weekly(intelligence) -> ReportDraft`
- `sales_leadership.py` — `render_sales_leadership(intelligence) -> ReportDraft`

Each renderer SELECTS a subset of the intelligence relevant to its audience and INSTRUCTS the
LLM (via system message, reusing the no-echo discipline from the content engine) to render that
subset as the audience-appropriate narrative.

Each renderer's selection logic, made explicit:

**Board** — emphasizes: period_summary (with delta), memory_highlights at high/moderate only,
campaigns by attributed pipeline contribution, open_questions framed as strategic risks/asks.
Omits: tactical content lists, watching list, individual run cost detail.
Length target: ~600–900 words. Tone: measured, accountable.

**CEO weekly** — emphasizes: 2–3 *notable_changes* with the "because" (one-line memory citation
where relevant), one "watch" item if material, one "what's next." Omits: raw funnel tables,
full campaign list, comprehensive production accounting.
Length target: ~150–250 words. Tone: scannable, signal-dense.

**Sales leadership** — emphasizes: top_content (especially anything sales can use), campaigns
in/near sales-handoff stage, accounts/segments showing intent (when data supports), what's
about to ship (production lane forward-looking). Omits: board-style efficiency framing, deep
memory pattern theory.
Length target: ~300–500 words. Tone: collaborative, "here's what we've got for you."

Each `ReportDraft` is the block-based content shape already in use elsewhere:
```
{content_type: "report_<audience>", blocks: [{kind, text, ...}], metadata: {...}}
```
Reusing the block structure means reports inherit the Library, grading, UTM (when relevant —
mostly null for reports), and approval gate paths for free.

## Reports are first-class assets
A generated report is an Artifact with `content_type` in
`{report_board, report_ceo_weekly, report_sales_leadership}`. This means it:
- Appears in the **Asset Library** with its own kind badge (treat as a sub-kind of content for
  filtering; library should be able to filter to "reports" specifically).
- Routes through the **approval queue** like content (`content_review_mode` governs — the same
  guardrail/gate_all/all_through setting). A report read by leadership is consequential output
  in public-facing terms — the human gate matters.
- Is **gradeable** by the existing quality loop (advisory grade against a report-appropriate
  rubric; reuse the rubric machinery, add a report-specific default rubric if `content_rubric`
  doesn't apply cleanly).
- Is **regenerable** ("give me something better") and **versionable** (parent_id chain).
- Can be **downloaded** from the Library as .md (already supported by the library's content
  download path).

## API
- `POST /api/reports/intelligence` — runs the engine, returns the structured intelligence
  WITHOUT generating a narrative. Useful for the UI to preview "what data the report will be
  based on" before incurring an LLM call. Scoped.
- `POST /api/reports/generate` — body: `{audience, scope, product_id?}`. Runs the engine, then
  the appropriate renderer, creates an Artifact (+ Run with cost), routes through the gate.
  Scoped. (Worker-driven — same async pattern as content generation. UI returns the run id
  immediately and polls.)
- `GET /api/reports` — list reports for the org (essentially a thin wrapper / filter over
  /api/assets with kind=report_*). Scoped.

Reports created via this path appear in the Library, the approval queue (if gated), and at
their dedicated detail view (same as any artifact).

## UI (minimal — guts only, polish deferred to Replit)
A new section/tab under Insights — "Reports" — or a sub-page reachable from Insights:
- **Compose**: audience selector (Board / CEO weekly / Sales leadership), scope selector
  (time-window OR campaign), product selector (defaults from the header selector), a "Preview
  intelligence" button (calls /intelligence, shows the structured object collapsed by section,
  so the user can see *what data* the report will draw from before generating), and a
  "Generate report" button.
- **Recent reports**: a list of the org's previously generated reports with audience, scope,
  date, status. Click → detail view (read the markdown rendered).
- **Detail view**: the report's markdown rendered, grade pill (if graded), regenerate-with-
  critique control (reuses the existing quality-loop "give me something better" path),
  download as .md, copy to clipboard.

The whole thing lives under Insights because it's the optimization/storytelling layer; do not
make it a top-level seventh step. The six-step workflow stays.

## Constraints (from CLAUDE.md)
- `scoped(Model, org_id)` for ALL reads/writes. Cross-org never appears (tested).
- ONE engine, THREE renderers — do not duplicate intelligence-building logic into the
  renderers (tested: the renderers must import the engine, not reimplement aggregation).
- Memory is consulted via the existing query_memory() service — do not bypass or reimplement.
  Honor the watching/insufficient discipline (insufficient → "watching" framing in the report,
  never a confident claim).
- Render strategies' LLM calls follow the synthesis.py fallback pattern: on no key, produce a
  deterministic template render of the intelligence object (basic but truthful — "Board update
  for Onit, period X to Y. Period summary: ... Memory highlights: ... Campaigns: ...").
  Reports must be generatable without an LLM key, just with less polish.
- The no-echo discipline from the content engine applies: intelligence-object fields land in
  the system message as guidance, never echoed verbatim into the report body. Add the same
  TONE_MARKER-style regression guard to the report generator's smoke test.
- Reports are versionable via the same parent_id chain as content; reuse, don't reinvent.
- The block-based content shape is reused; do not introduce a new artifact shape for reports.
- The dashboard's baseline-vs-attributed discipline propagates: untagged metric_points are
  funnel backdrop only, never quoted as something marketing drove. (Same enforcement that the
  memory layer now applies.)
- No new dependencies. No schema change should be needed — reports are artifacts with new
  content_type values. If a tiny helper column is unavoidable, mirror in sql/schema.sql.
- Don't touch the TS app or .replit's [deployment] block.
- Keep `python -m scripts.smoke` green. ADD tests (hermetic — stub the LLM):
  (1) Engine: build_report_intelligence for a populated org returns the full ReportIntelligence
      shape with non-null sections; honesty_notes is populated when prior-period data is absent.
  (2) Empty scope: build_report_intelligence for an empty time window returns a truthful
      minimal object (no confabulation), honesty_notes explicitly says "no data in scope."
  (3) Memory propagation: an insufficient memory pattern lands in `watching`, NEVER in
      `memory_highlights`; high/moderate patterns land in `memory_highlights` with evidence.
  (4) Three audiences differ MATERIALLY (the load-bearing test): from the same intelligence
      object, render_board / render_ceo_weekly / render_sales_leadership produce drafts whose
      block content differs in non-trivial ways — assert lengths differ by audience target,
      assert audience-specific sections appear/absent per the spec (e.g. CEO weekly has no
      campaign list block; board has no "what sales can use" framing).
  (5) Reports are first-class assets: a generated report is an Artifact with content_type
      report_<audience>, appears via /api/assets, downloadable as .md, gradeable, regenerable
      via parent_id.
  (6) Approval gate honored: with content_review_mode=gate_all, a generated report lands in
      the approval queue as a proposal; with guardrail, it auto-readies unless a guardrail
      trips; with all_through, auto-readies.
  (7) Tenant isolation: /api/reports/* cross-org access denied (403/404); reports generated by
      Acme never appear in Onit's library or list.
  (8) No-echo discipline: a brand_voice or instruction marker in the system message MUST NOT
      appear in the rendered report (reuse the TONE_MARKER pattern).
  (9) Deterministic fallback: with no LLM key, generation still produces a basic-but-truthful
      report from the intelligence object (assert it contains the period summary numbers and a
      memory highlight if any exist).
  (10) Untagged data honesty: untagged metric_points are reflected as backdrop in the funnel
       numbers but are NEVER claimed in the report as something marketing drove (assert the
       report copy does not attribute untagged organic to a campaign or to marketing action).

## Done looks like
- Pick an audience (board / CEO weekly / sales leadership), a scope (time-window or campaign),
  click Preview Intelligence → see the structured object the report will use. Click Generate
  → a markdown report appears in seconds, routed through the gate (queue or auto-ready per the
  org's review mode), gradeable, regenerable, appearing in the Library with a Reports filter.
- The three audiences produce **materially different** reports from the same underlying data
  — different selection, different framing, different lengths, different "what the report is
  for."
- Reports cite memory patterns with evidence ("LinkedIn drove 2.2 conversions per 100 clicks
  for GC — X conv across N data points"). Insufficient patterns appear as "watching," not as
  findings. Untagged volume stays as backdrop, never claimed.
- The system works without an LLM key (deterministic fallback). Smoke green with the ten new
  tests. Pushed to main.

## Explicitly out of scope (DO NOT build — future)
- Slide-outline rendering (titles + bullets per slide for PowerPoint/Google Slides). The block
  structure supports it; future render strategy. Signpost it.
- Slack-message rendering (short-form for posting to a channel). Same — future strategy.
- Auto-send to Slack/email/etc. Never auto-published. Manual share / copy out only.
- Scheduling ("send this every Monday"). Future Strategy Layer adjacent.
- Predictive claims ("we expect Q3 to..."). Reports describe what HAS happened; they don't
  forecast. Open questions can be surfaced as questions, never as predictions.
- Multi-org / portfolio reports. Org-scoped only.
- Custom audience templates beyond the three. Spec the three cleanly; templating new audiences
  is a future build that should be a thin addition once the engine + render pattern is proven.
- Brand-asset embedding (logos, colors) in report output. Future, paired with org-design-system
  build.
- Visual rendering (charts embedded in report body). Future. Numbers in prose for v1.
- Editing reports in-place. Regenerate-with-critique is the v1 path for revision.
